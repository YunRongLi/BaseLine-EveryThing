# Security Code Review (CWE-699 Software Development View)

## Overview

This skill establishes a systematic, authoritative security review methodology based on the MITRE CWE-699 (Software Development) view. It provides full coverage across all 40 software development weakness categories, structured into domain-specific reference checklists.

When conducting a security review, assess the codebase against these guidelines, identify design and implementation flaws, and produce actionable findings adhering to the standardized reporting format.

---

## Security Review Workflow

Follow this 4-step workflow when auditing code:

### Step 1: Attack Surface and Context Triage
* Identify Trust Boundaries: Map all entry points where untrusted data enters the component (network sockets, IPC, command-line arguments, environment variables, device files, sysfs/procfs, configuration files).
* Determine Threat Context: Identify the operational privileges of the component (kernel space, root daemon, unprivileged user, sandboxed process) and assets under protection (memory integrity, private keys, authentication tokens, hardware configuration).

### Step 2: Vulnerability Inspection by Category
* Select Relevant Domain Modules: Inspect code against the specialized checklists in the `references/` directory.
* Apply Negative Testing Mental Model: Evaluate how the code handles invalid lengths, out-of-order calls, resource exhaustion, unexpected concurrency, and malformed inputs.

### Step 3: Severity Assessment
Classify each confirmed finding using the standard 4-tier severity matrix:
* Critical: Direct remote code execution, unauthenticated privilege escalation to root/kernel, arbitrary memory overwrite, or complete bypass of authentication.
* High: Authenticated privilege escalation, local denial of service via kernel crash / panic, information disclosure leaking cryptographic keys / credentials, or command injection with restricted parameters.
* Medium: Out-of-bounds read with limited disclosure, race conditions causing transient denial of service, improper error handling causing uncontrolled resource consumption, or weak cryptographic algorithms in non-root contexts.
* Low: Missing defensive checks that are not currently reachable by external input, overly verbose diagnostic logging without direct secret exposure, or code complexity issues elevating future maintenance risk.

### Step 4: Vulnerability Reporting and Remediation
Synthesize all findings into the required reporting structure, complete with root cause analysis and verified patch guidance.

---

## Standard Finding Output Format

All security findings generated by this skill must adhere to the following schema:

```markdown
### [Finding ID]: <Brief Title Describing Vulnerability>

* Severity: <Critical | High | Medium | Low>
* CWE ID: <CWE-XXX: Weakness Name>
* Location: <file_path>:<line_number>
* Root Cause Analysis:
  <Detailed technical explanation of the flaw, how the untrusted data flows into the vulnerable operation, and why existing checks fail or are absent.>
* Exploit Scenario / Impact:
  <Practical scenario demonstrating how an adversary can trigger or leverage the flaw, and the resulting impact on confidentiality, integrity, or availability.>
* Remediation:
  <Actionable guidance or code diff demonstrating how to eliminate the vulnerability safely.>
```

## Core Defensive Principles

1. Fail-Closed Defaults: When encountering an unexpected condition or error, reject the request, revoke access, and abort safely.
2. Principle of Least Privilege: Every module, process, and thread must run with the bare minimum permissions necessary to perform its task.
3. Complete Mediation: Check permissions on every access, not merely upon initial connection or open.
4. Input Distrust: Treat all external data across trust boundaries as malicious until explicitly validated against a strict allowlist.
5. Defense in Depth: Layer independent security mechanisms so that the failure of one defensive control does not result in compromise.
